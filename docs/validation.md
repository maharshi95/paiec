# Local validation: train/eval splits and how they are configured

The hosted metric and protocol are in `evaluation.md`. Which benchmarks are eligible is in `benchmark-selection.md`.

## Why benchmark-level splits
The hosted test uses **benchmarks never seen in training** (benchmark-level cold start). So every local split holds out whole benchmarks. A random row or item split would leak each benchmark's offset and its item difficulties.

## Mechanics (`src/paiec/experiment.py`)
Config keys:
- `data.benchmarks`: the universe that is loaded.
- `cv.test_benchmarks`: the list of folds. An entry is either a benchmark name (leave-one-benchmark-out) or a **list** of names held out together (grouped fold).
- `cv.train_benchmarks`: optional; restricts training to these benchmarks, minus the fold. Default is all loaded benchmarks minus the fold.

For each fold:
1. `train = universe (or train_benchmarks) − fold`, and `predictor.fit(train)` runs once per fold.
2. For each seed in `cv.seeds`, the fold's benchmarks are replayed with the hosted protocol (`sim/replay.py`):
   - every (subject, benchmark) pair with ≥ `cv.min_items` (80) distinct items;
   - a 50/50 acquisition/evaluation split fixed by `cv.split_seed`;
   - candidate order and revealed trials set by `seed`.

   Optional speed caps are `cv.max_subjects_per_benchmark` and `cv.max_eval_items_per_pair`.
3. Metrics are computed per pair, then averaged.

Outputs in `runs/<name>/metrics.json`:
- `alc`: mean over folds of the fold's pair-macro ALC (each fold weighted equally);
- `alc_pairs`: mean over all pairs;
- `benchmarks`: per-benchmark ALC;
- per-budget Brier and ECE.

`pairs.csv` enables paired comparisons, since runs with the same `split_seed` and `seeds` see identical pools, orders and draws.

## The two protocols in use
| | **ref6-LOBO** (`configs/base.yaml`; every result in `results.md` up to 2026-10-22) | **panel-5fold** (`configs/sel/*`, generated by `scripts/make_selection.py`) |
|---|---|---|
| universe | the 6 reference benchmarks in `data/raw` | 208 benchmarks (207-benchmark train pool + ref6), each capped at 100K responses by subject subsampling |
| folds | 5 single-benchmark folds: matharena, mmdocrag, multi_swebench, real_webagents, researchcodebench. swe_rebench (1 subject) is train-only | 57 panel benchmarks in **5 grouped folds of 11–12**, assigned round-robin in domain-sorted order so each fold mixes domains |
| training per fold | the other 5 benchmarks | variant: `sel_pool` = all 207 minus the fold; `sel_panel` = the other panel folds; `sel_ref6` = the 6 reference benchmarks |
| seeds / caps | 3 seeds, ≤200 eval items per pair | 1 seed, ≤20 subjects per benchmark, ≤100 eval items per pair |
| cost | 5–10 min per run on 1 CPU | one Slurm CPU job per variant (8 CPUs, 60 GB) |
| weakness | 5 test benchmarks: high variance, easy to overfit | hyperparameters tuned on the same folds they are reported on |

## Recommendation: add a locked hold-out set (not implemented yet)
Every number so far is reported on the folds used to choose settings: the radius, beta_var_mult, item_target and the training pool. With ~30 configurations compared, that is optimistically biased. The cure is a **dev / hold-out split of benchmarks**:
- **dev** (≈ 45 panel benchmarks): grouped 5-fold CV as above. Use it for every comparison and sweep.
- **hold-out** (≈ 12 panel benchmarks, about 2 per major domain): never used for tuning. It is evaluated only for milestone configs (e.g. before each Codabench submission and for the final report), training on everything except the hold-out. The report quotes this number.
- Keep the six reference benchmarks in dev, since all history is on them.
- The hold-out must also be excluded from the training pool whenever dev runs train. This mimics the hosted test, where test benchmarks were never released.

Codabench formative feedback is the true external check, but each feedback run is a fresh ≤1,000-pair sample, so it is noisy.
